# Ojo Israel Content Research & Editorial Plan

## Purpose

This content plan turns real questions about AI automation, n8n, Make.com, CRM automation, AI agents, RAG, and business workflows into a focused publishing roadmap.

The goal is not to publish pages simply because a keyword exists. Each article should help a real reader solve a real problem and should add practical experience, implementation detail, examples, limitations, or lessons that are useful beyond a generic AI-generated summary.

## Editorial principles

Every article should:

1. Be written primarily for people, not search engines.
2. Answer the main question early and clearly.
3. Add first-hand implementation detail where possible.
4. Use accurate, current information and clearly distinguish examples from universal rules.
5. Avoid unsupported claims, fake statistics, fake case studies, fabricated experience, and invented quotes.
6. Avoid keyword stuffing and repetitive pages targeting minor keyword variations.
7. Avoid creating many near-duplicate pages simply to capture search queries.
8. Explain limitations, failure cases, tradeoffs, and when the recommended approach may not be appropriate.
9. Link to relevant guides, projects, documentation, and supporting resources.
10. Include a natural connection to a relevant project or service only when it genuinely helps the reader.
11. Be reviewed before publishing, especially where tools, APIs, pricing, product features, or policies may have changed.
12. Use AI as an assistant for research, structure, editing, or ideation, while adding original analysis and implementation evidence.

## Standard article structure

Use this structure when it fits the topic:

1. Direct answer / short introduction
2. The business or technical problem
3. When this approach makes sense
4. Architecture or workflow diagram
5. Step-by-step implementation
6. Example configuration or decision logic
7. Error handling and edge cases
8. Common mistakes
9. Costs or operational considerations when relevant
10. When not to automate / alternatives
11. First-hand implementation notes
12. Related guides and project links
13. Short conclusion
14. Natural CTA

Do not force every section into every article. The structure should serve the reader.

## Evidence standard

For implementation articles, include as many as are genuinely available:

- Original workflow diagram
- Screenshots of the actual workflow
- Node/module names
- Sample input and output
- API request/response examples where safe
- Database fields
- Validation rules
- Branching logic
- Error handling
- Testing notes
- Lessons learned
- GitHub implementation
- Links to official documentation for changing technical details

Never expose secrets, API keys, private customer information, or credentials.

## SEO requirements for every article

### Title

- One clear primary topic.
- Descriptive and concise.
- Matches the actual page.
- Avoid repetitive keyword variations.
- Include the brand only when useful.

### Meta description

- Accurately summarize the page.
- Give the reader a reason to click.
- Do not keyword-stuff.
- Do not promise something the article does not contain.

### Main heading

Use one clear H1 that matches the article's primary purpose.

### URL

Use a short, descriptive, stable slug.

Example:
articles/ai-lead-qualification-n8n.html

### Content

- Answer the main question directly.
- Use useful headings.
- Include examples and practical details.
- Use descriptive link text.
- Add original evidence where available.
- Avoid padding articles to reach an arbitrary word count.

### Images

When images add genuine value:

- Use relevant original workflow screenshots or diagrams.
- Add descriptive alt text.
- Do not use images purely as decoration.
- Do not use misleading image metadata.

### Structured data

Where appropriate, use valid structured data that accurately represents visible page content.

Never add structured data for content that is not actually visible on the page.

### Technical SEO

Check before publishing:

- Indexable page
- Correct canonical URL
- Crawlable internal links
- Included in sitemap
- No accidental noindex
- Descriptive title
- Useful meta description
- Mobile-friendly layout
- Fast enough page experience
- HTTPS
- Clear H1
- Correct heading hierarchy
- No broken links
- Images have useful alt text
- Article links are discoverable from other pages

## Quality gate before publishing

Ask:

1. Would a real business owner or automation practitioner find this useful?
2. Does the article answer the question better than a generic AI summary?
3. What original information, implementation detail, or analysis does this page add?
4. Did I verify technical details that may have changed?
5. Did I explain limitations and edge cases?
6. Are examples clearly presented as examples?
7. Are claims supported by evidence where needed?
8. Are links relevant and working?
9. Is the page easy to read on mobile?
10. Would I still publish this if Google did not exist?

If the answer to the last question is no, revise the article.

## Important policy rule

Do not turn this list into 50 thin pages simply because there are 50 questions.

Related questions should sometimes be combined into one comprehensive guide when they serve the same search intent. Google specifically warns against creating large amounts of low-value content for search manipulation. The publishing plan should therefore be treated as a research backlog, not a requirement to publish exactly 50 separate pages.

The target is useful, original, expert-led content, not maximum page count.
